# The macOS app

`ui/SkillctlApp/` is a SwiftUI application that fronts the CLI. It is deliberately thin: the app never reads the registry, the store or the event log itself. Each screen runs `skillctl --json <command>` through `Process`, decodes the JSON with `Codable` types that mirror the CLI's output field for field (`Models.swift`), and renders it. Mutating actions run `skillctl --json --yes <command>` and then reload the data they changed. This keeps one implementation of every rule and makes every click reproducible in a terminal: the Console pane lists each invocation with its arguments, working folder, exit code and output.

## Layout

| File | Role |
|---|---|
| `Package.swift` | SwiftPM executable target, macOS 14 deployment target, Swift 5 language mode (tools version 5.10) so strict concurrency does not block a small app |
| `CLI.swift` | `CLI`: binary discovery (Settings path, then `target/debug/skillctl` found by walking up from the executable so a checkout's debug build beats an installed, possibly older, copy, then `~/.cargo/bin`, Homebrew, `PATH`), `missingCommands` (the `requiredCommands` that `--help` does not list; an outdated binary is reported, not used), `run` (background queue, both pipes drained concurrently, stdin closed, optional `SKILLCTL_HOME` and extra environment), `decode`, `perform`, and `failure(of:)`, which turns the CLI's `{"error","message","hint","exit_code"}` object into a `CLIError`. `CommandRun` is the console record. |
| `Models.swift` | Codable mirrors: `Project`, `Instance`, `Artifact` (the `artifacts` row), `Draft` (the `drafts` row), `HookEntry`, `DoctorReport` with `Problem`, `Telemetry`, `Harnesses`, `MCPAudit`, `LogSummary` with `LogWindow` and `LogAlert`, `Finding` (validate and lint), `StatusReport` |
| `AppState.swift` | `@Observable @MainActor` store: settings persisted in `UserDefaults`, loaded data, a `busy` set, the console, `lastError`, and one method per CLI action. `doctor` is decoded regardless of exit status because it exits 1 while problems remain; `validate` and `lint` accept exit 3 for the same reason. |
| `ContentView.swift` | `NavigationSplitView` with the `Screen` sidebar in sections (Dashboard; Library: one `.kind(id)` row per `ArtifactKind` plus Store; Workspace: Projects; Health: Doctor, Log, Quality), badges (drafts per kind, unhealthy hooks, unused versions, doctor problems, warning alerts), the toolbar, the error alert, the `VSplitView` console. Every row carries an explicit `.tag(Screen)`: the list's selection is a `Screen`, and without the tag SwiftUI tags rows with their `id` and selection silently never matches (the first version's sidebar did nothing for that reason). |
| `KindView.swift` | The library screen for one `ArtifactKind` (`Models.swift` carries the kind table: title, root document, where a pin links, summary, symbol). `KindView` merges `drafts` and `artifacts` of the kind into one `Entry` per name (draft plus versions) and shows them as a searchable list (drafts first; subtitle with latest version, older count, pin or registration state) beside `ArtifactDetail`: header with the description from the root document, a draft card (Reveal, Validate `<name>@draft`, Derive for agents, Seal with a bump picker), for hooks a registration card (link state, events, Repair, Remove, or Register the latest), and a versions table (newest first; pins or registration, uses, last used, unused badge) with actions on the selected version (Validate, Edit as draft, Pin into project or Register this version, Delete version through `uninstall <name>@<version>`, disabled while pinned with the pins in the help text); a header menu deletes every version (`uninstall <name>`) when none is pinned. Both deletes confirm first and rely on the CLI's own refusal of pinned versions, so the UI never has to reimplement that rule. Under the versions table a Document card shows `skillctl show <name>@<version>` (or `@draft`, switchable when both exist): the root document with line numbers and text selection, and every bundled file (references, scripts, schemas) as a chip that shows that file in its place (`selectedFile`, read through `FileText`); Open and Reveal act on the file shown, and the card reloads when the selected version changes. New (`new --kind`) and Install sheets sit in the toolbar. The first version listed every version as its own row and the nine superseded 0.1.0 skills doubled the table; grouping by name is what made the screens readable. Rows and the header carry a scope badge from `Scope.of(versions)` (`global` when any version is pinned `global`, `project` when any is project-pinned, `unused` when nothing pins it); skills, commands and agents get Make global / Remove from global (`global add` / `global remove`, disabled while a project pins it); the toolbar's Clean up unused opens `BulkDeleteSheet` with that kind's unused versions. |
| `StoreView.swift` | The whole store as a hierarchical `Table(rows, children:)`: one `StoreRow` per artifact name (kind badge, union of pins, best use count, `all unused` when every version is) with its versions as children, newest first. Kind chips with counts, search and an unused toggle filter the rows; a summary bar counts versions, artifacts and unused ones. Selecting a row opens the system `.inspector` with `ArtifactDetail` for that artifact, so the Store and the kind screens share one detail view. `CleanupSheet` runs `--dry-run --yes gc --keep n` (`GcReport`), lists what would go, and only then offers the delete, which runs the same `gc`. The table is multi-selectable; Delete selected (`BulkDeleteSheet`) expands selected artifact rows to their versions, splits them into deletable and pinned (named, with the hint to unpin first) and runs `uninstall` per deletable version through `AppState.uninstallMany`; Unused only plus ⌘A is the bloat-review path. `InstallSheet` lives here too. |
| `LogView.swift` | `log summary` and `log usage` side by side: a grouped bar chart of the window's `daily` series (prompts, activations, subagent runs, compactions), metric tiles including activation through the hook (`hook_followed` of `hook_shortlists`), alerts, and a Cost and tokens card from `UsageReport` (cost, cost per prompt, output tokens per prompt, cache hit ratio tiles; cost per day and output tokens per prompt charts; cost by model; a per-day table). Usage is loaded on demand (`AppState.loadUsage`) because ccusage can take several seconds, and the card shows that state. |
| `TelemetryView.swift` | `TelemetrySection`, the Log screen's collector card. While `TelemetryStatus.healthy` is false (settings not pointed at the collector, or it is not running), it shows a checklist of settings, login service and collector with the reason each is missing, plus one Turn on or Repair button (`AppState.setTelemetry`, which re-runs doctor afterwards). Once healthy, it shows tiles for cost, the share spent inside skills and in subagents, and output tokens; cost bar charts by skill, agent and model; and tool runs with failures from `TelemetryReport`. If the LaunchAgent runs a different binary than the app, a "Use this app's" button repoints it. |
| `DoctorView.swift` | A status card (Healthy or the remaining count, last run time, advisory counts, Run again and Fix), a Problems section only when there are problems, and the advisory sections with severity counts in their headers; every row has Copy fix (clipboard) and Reveal for its path; Harness versions shows the detected versions with their history. |
| `DashboardView` (needs-attention list, overview tiles, a tile per kind, last-week metrics), `ProjectsView`, `QualityView` (findings, then a scope card: `show` of the chosen version for validate, `lint --files` of the chosen folder for lint, loaded as soon as the choice is made; a third tab renders `rules` grouped by catalog group, filtered by kind and searched by ID or text), `SettingsView`; `HooksView.swift` (the registration table) | One file per screen; sheets for attach, add pin, install, new, seal, derive and pin; confirmation dialogs before detach, garbage collection and hook removal |
| `Shared.swift` | `FileLinks` (Preview, Open and Reveal for any path, used by findings, doctor problems and the Quality scope cards), `FilePreviewSheet` and `NumberedText` (wrapped, numbered lines with one highlighted and scrolled to), `FileText` (UTF-8 up to 1 MB, otherwise a reason); `SeverityBadge`; `FindingsTable` (validate and lint results: a summary line with error, warning and note counts and the folder every finding shares, then a `List` grouped by severity whose rows show the rule in monospace, the message, the hint behind a wrench icon and the file name with line and a Reveal link); `ProblemsList`, `StatTile`, `Panels` (NSOpenPanel wrappers, reveal in Finder) |
| `Scripts/bundle.sh`, `Resources/Info.plist` | `swift build`, `cargo build --release --locked` (or `scripts/release/build-universal.sh` with `UNIVERSAL=1`, or a prebuilt `SKILLCTL_CLI`), and a hand-made `Skillctl.app` in `dist/` with the app at `Contents/MacOS/Skillctl` and the CLI at `Contents/Helpers/skillctl`; unsigned. The CLI must not go into `MacOS/`: the default filesystem is case-insensitive, so `skillctl` there *is* `Skillctl`, and the first attempt overwrote the app with the CLI. The script quits a running copy first because `open` only activates an already running app. |
| `Tests/SkillctlAppTests/EndToEndTests.swift` | XCTest, `@MainActor`. Finds `target/debug/skillctl` by walking up from the test file (skips if the CLI is not built), builds an `AppState` with a private `UserDefaults` suite, a temporary `SKILLCTL_HOME` and `HOME` redirected into the temp folder, then runs the whole workflow against the real binary: init, `new` a skill and a hook through the drafts listing, validate the draft, `seal`, `edit` a version back into a draft and seal it with a minor bump, `new` an agent and `derive` its Cursor override, attach a Git folder to a new project with a pin, register the hook (settings land in the redirected `HOME`), write a log and read the summary, doctor with its advisory sections (Cursor's version from the log), status, validate, lint, a failing `add`, unpin, unregister, detach. Two more tests cover the outdated-binary report (a fake `skillctl` whose `--help` lacks `log`) and the discovery order. |

## Layout

All spacing comes from `Metrics` in `Shared.swift`: `page` (24, the outer margin of every screen and sheet), `section` (20, between sections), `card` (14, inside a card), `gap` (12, between items), `header` (8, between a card's title and body), `tight` (6), `listWidth` (280, the list column of list-plus-detail screens) and `radius` (10). Three helpers apply them: `pageLayout()` for scrolling screens, `barLayout()` for full-width filter and summary bars, and `SheetLayout` for dialogs. `CardGroupBoxStyle` is set once at the root (and on the Settings scene), so every `GroupBox` is the same card: title row flush with the card's left edge, then the body on a rounded surface. The style wraps the body in one `VStack`, because a `GroupBox` body with several children (an `if` plus a `ForEach`) would otherwise become one card per child. List-plus-detail screens use an `HStack` with a fixed-width list and a `Divider` rather than `HSplitView`, which ignored its width limits and let the list take half the window. Findings are grouped rows in a stack, not a `List`, so they fit both a scrolling page and a sheet; a `List` with flexible frames outside a scroll view left the Quality screen, sidebar included, blank.

## Reviewing screens without a screenshot permission

`SKILLCTL_APP_SNAPSHOT=<folder>` makes `ContentView` resize the window to 1280×820, load everything, walk every `Screen`, capture the window with `CGWindowListCreateImage` and write `<folder>/<screen>.png`, then quit. An app may capture its own windows without the Screen Recording permission that `screencapture -l` from a terminal needs, which is what makes this usable from an agent session. Two earlier attempts did not work and are worth not repeating: `NSView.cacheDisplay` and `CALayer.render(in:)` capture only AppKit-backed views (tables), and `ImageRenderer` renders nothing inside a `ScrollView`, which is AppKit-backed on macOS. One more trap: macOS stops drawing a window that stays occluded for a couple of seconds, and a capture of such a window comes back blank, so the snapshot run activates the app, floats the window and orders it front before each capture. `SKILLCTL_APP_SNAPSHOT_VALIDATE=1` additionally runs a validation on the Quality screen so its findings layout can be reviewed, and `SKILLCTL_APP_SNAPSHOT_ONLY=<screen id>` (for example `Quality` or `kind:skill`) captures a single screen.

## Decisions

1. **CLI, not a library.** Linking the Rust crate through a C ABI would have meant a second public surface and a build that needs both toolchains. The JSON output already exists for scripts, is covered by the CLI's tests, and is versioned with the binary the app finds, so the app follows whatever `skillctl` is installed.
2. **No prompts, ever.** Every call passes `--yes` where a prompt is possible and closes stdin, so a command can never hang on a question; anything that deserves a confirmation is confirmed in the app instead (detach, gc, hook remove).
3. **Working folder is a parameter.** Commands that act on the current folder (`attach`, `detach`, `status`, `lint`) receive the chosen folder as the process's `currentDirectoryURL`; the app itself has no notion of a current project.
4. **Failures are the CLI's words.** The error alert shows the CLI's `message` (and `hint` as the recovery suggestion), never an app-side paraphrase.
5. **Not in the Rust CI.** `ci.yml` is untouched; `swift.yml` runs only when `ui/**` changes: it builds the CLI, builds the app, runs `swift test` and uploads the bundle as an artifact.
6. **The app carries the CLI.** `CLI.bundledLocation` (`Contents/Helpers/skillctl`) is the second candidate after an explicit Settings path, so an installed app needs no separate CLI and app and CLI cannot drift apart; `AppState.linkCommandLineTool` symlinks it into `~/.local/bin` on request, replacing only an existing symlink. The CLI stays installable alone for terminal-only users.
7. **Development builds win.** The user tests with the debug build until a release is cut, and an installed `~/.cargo/bin/skillctl` from an earlier release produced `unrecognized subcommand 'log'` in the first version of the app. Hence the discovery order and the `--help` capability check.
8. **The collector runs the app's CLI.** The Log screen's switch calls `telemetry enable` through the same CLI as every other screen. The LaunchAgent records the binary that wrote it, so turning the collector on from the app makes it run `Contents/Helpers/skillctl`. Turning it on is never automatic, because it writes `~/.claude/settings.json` and installs a login item.

## Running

```
ui/SkillctlApp/Scripts/bundle.sh [debug] && open ui/SkillctlApp/dist/Skillctl.app
```

or `swift run` inside `ui/SkillctlApp/`. Settings (⌘,) take an explicit binary path and a `SKILLCTL_HOME` override, which points the whole app at another home, for example one of the CLI test suite's temporary homes while debugging.
